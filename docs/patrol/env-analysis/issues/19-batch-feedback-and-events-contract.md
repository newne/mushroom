# 19 — 批次内「环境反馈值 + 调整事件」取数契约（含首日剔除与时间基准）

**Spec:** ../spec.md §2.2、§2.4、§2.5、§2.6；ADR-0020（批次身份）、ADR-0022（主体=实际参数）、ADR-0023（小时聚合）

**归属：** 环境官（`analysis/**`）。**契约已定稿（Chief 2026-10-14 裁四条）；本票仍不动 DDL、不改代码。**

**地位：** 这是"调控指令 v1（建议层）"的**输入契约** —— 一期交付收窄到**菌簇长度与直径**
之后，指令要用的就是这两样：**入库以来的环境参数反馈值** + **关键节点的调整值**。

## 0. 用户裁定（2026-10-14）

1. **记录重点改为**：入库以来的**环境参数反馈值** + **关键节点的调整值**（逐条操作日志 +
   设定值变更），用途是**后续直接输出调控指令**。口径照旧：`/operations` 是权威源、**不预聚合**；
   设定值变更读 `/operations`，`device_setpoint_changes` **只作交叉验证**。
2. **入库时间以平台读取为准**，不要从 0 自推；**生长天数按平台值算**
   （票 13 的 pgsql `MushroomBatchYield.in_date`）。
3. **入库首日的温湿度必须剔除**（受原环境因素影响、波动大）：**原始数据仍保留、不删**，
   只在 `ranges`/统计/学习里排除，并带 `first_day` 标记。

## 1. 时间基准（裁定 2）

| 项 | 口径 | 依据 |
| --- | --- | --- |
| 入库日期 | **`mushroom_batch_yield.in_date`**（pgsql，DATE） | 票 13 §1.1；**不从"数据里第一次出现"自推** |
| 我们口径的第 N 天 | `(某日 − in_date).days`（入库当天 = **0**） | spec §2.7 第一套 |
| 生产口径的生长天数 | 上值 **+1**（入库当天 = **01**） | spec §2.7 第二套；两套并列显示，不合并 |
| 面板校验 | `TD1_Q{1..4}MDINFO01` 的 `InDayNum` 作**第三个数** | ADR-0020；不一致时告警 + 双显，**不取平均** |

⚠️ 连带一条：`in_date` 是 **DATE 精度**，**没有"入库时刻"**。这直接决定 §2 的规则怎么落。

## 2. 入库首日剔除（裁定 3）—— **已裁定：按自然日（方案 b）**

**Chief 2026-10-14 裁定**：`in_date` 只有 DATE 精度这条说服了裁定 —— **上一轮"首个 24 小时"口径作废**，
改成"`ts` 日期 == `in_date` 当天整日 00:00–24:00 剔除"；**(a) 弃用，且不许为它编一个"入库时刻"的源。**

| 方案 | 规则 | 结论 |
| --- | --- | --- |
| (a) 入库时刻起算 24 h | `[in_time, in_time+24h)` | ❌ **弃用**：没有时刻的权威源（`in_date` 是 DATE，面板 `INFO01` 只有 `InYear/InMonth/InDay`），不许编 |
| **(b) 自然日（采用）** | 行的 `ts` 日期 == `in_date` 即剔除 | ✅ 当场可实现，只用已有权威 |

**采用 (b) 的两条论据（可复验）**：① 两种真实入库时刻下，(b) 覆盖的都是该覆盖的东西 ——
入库在当天 18:00 时，00:00–18:00 是**上一批的尾巴**、18:00–24:00 是本批首日波动段，
整天剔除两头都对；入库在 00:05 时 (b) ≈ (a)。② 与"入库当天 = 第 0 天"及 D 分档天然一致。

**代价（写明）**：入库很晚（如 22:00）时会多剔几小时 —— 但那些小时**本来属于上一批**，
多剔的方向是安全的。

**标记方式（已批准）：`first_day` 读时派生、不落列。** 它依赖 `in_date`；平台更正 `in_date` 时
派生值自动跟着变，库里不留"当时以为的首日"。**原始小时行一律保留**（ADR-0023），
排除只发生在统计与学习侧（可用 `first_day` 复算回去）。

## 3. 取数接口与字段（裁定 1）

### 3.1 批次内环境时间序列

新增 `GET /environment/batch-series?room_id=&entry_date=&granularity=hour|day`

| 字段 | 类型/单位 | NULL / 备注 |
| --- | --- | --- |
| `ts` | TEXT，本地 ISO8601（整点） | 库里就是小时聚合（ADR-0023） |
| `zone` | TEXT，库房号 | 611/612/607/608 |
| `temp_c` / `rh_pct` / `co2_ppm` | REAL（℃ / % / ppm） | **整列无源 ⇒ NULL**（不写 0） |
| `temp_min` / `temp_max`、`rh_min` / `rh_max`、`co2_min` / `co2_max` | REAL | 采样点级真实极值 |
| `lamp_on_min` | REAL，**分钟**（设定量折算，不是 lux） | 无源 ⇒ NULL |
| `lamp_state` | REAL，枚举 **0=自动 1=手动 2=停止 3=关闭**（该小时众数） | 分类量，**不是"灯亮没亮"** |
| `n` | INT，条 | 该小时实际采样点数；**< 60 即该小时有缺口**，不补不插值 |
| `growth_day` | INT | **我们口径**：入库当天 = **0** |
| `growth_day_prod` | INT | **生产口径**：入库当天 = **01**（上值 +1） |
| `inday_panel` | INT，**可空** | 面板 `INFO01` 的 `InDayNum`，第三个数校验 |
| `first_day` | BOOL | **派生**：`ts` 日期 == `in_date`（§2 方案 b）；**默认排除出统计** |

**三值不一致（`growth_day` / `growth_day_prod` / `inday_panel`）⇒ 告警 + 并列显示，
绝不取平均、绝不合并成一个数**（ADR-0020 的双显口径）。

聚合口径不新增：**小时是落库粒度，天由小时行再折一层**（均值按 `n` 加权，断档不拽偏均值）。

### 3.2 全部调整事件

**沿用 `GET /operations?zone=&start=&end=&limit=`**（权威源、逐条、不聚合），字段同 `operations` 表：
`ts` / `zone` / `device_code` / `device_name` / `point_code` / `point_name` / `value` /
`operator` / `source`（现场/远程）/ `content`（平台原话）。

⚠️ **"从 → 到"是派生量，不是平台给的**：审计只给"改成了什么"。
要看"从什么改到什么"，必须按 `(zone, device_code, point_code)` **对相邻两条事件做前值差分**。
所以契约里写清：**`/operations` 给事件流；"从→到"由读取方按上面的键排序后差分**（同一时刻多条、
跨批次边界要当心）。`device_setpoint_changes` 只作**交叉验证**，不作为事件源（ADR-0022 口径）。

### 3.3 两路合流（指令建议层的输入）

一条响应里给"当期环境反馈 + 同期调整事件"，但**不预聚合、不做因果判断**：
接口只负责把"当时是什么环境 + 那时谁改了什么"配对拿出来；"该不该调"是建议层的事。

## 4. 幂等与不变量

- 环境行 PK `(ts, zone)`、事件行 PK `(ts, device_code, point_code)`：重发覆盖、不翻倍。
- **不预聚合**：事件逐条留（ADR-0023 补记）；环境只留小时聚合，原始分钟序列按窗口现取
  （`GET /environment?granularity=raw`，上限 6 h）。
- **剔除不删数据**：首日排除只发生在统计/学习侧；库里原始行照旧（可用 `first_day` 复算回去）。
