# ADR-0026：源历史数据在 TDengine（只读），业务数据在 PostgreSQL / Redis

日期：2026-10-15
状态：**生效**（用户 2026-10-15 明确裁定）
相关：ADR-0021（环境参数权威）、ADR-0023（小时聚合存储）、`docs/patrol/env-baseline/spec.md`

## 背景

环境数据有两个截然不同的角色，此前没有被写成一条硬规则：

1. **源历史数据**：现场设备每分钟一条的原始序列（温湿度、CO₂、补光灯状态与设定），存在 **TDengine**（库 `data1`，容器 `tools_taos`，REST `:6041`）。它是**唯一不可再生的原始记录**。
2. **业务数据**：从原始序列派生出来的、供分析与界面使用的东西（小时聚合行、批次台账、区间表、快照等），存在 **PostgreSQL**；热数据缓存用 **Redis**。

混用这两种角色会出事：往 TDengine 写"加工过的数据"，等于在一个**只该追加原始观测**的库里掺入派生结果，事后无法区分"实测"与"算出来的"；而把原始分钟序列复制进 PostgreSQL，则会产生第二份权威（ADR-0023 已因此裁定原始序列**不落库** PG）。

## 决定

1. **TDengine 只读**。任何代码路径、脚本、一次性操作**都不得**对 TDengine 执行写入或 DDL——包括 INSERT、CREATE、ALTER、DROP、以及任何"顺手补一条"的动作。
2. **业务数据一律落 PostgreSQL**；热数据或短期缓存用 **Redis**。
3. 需要"把 TDengine 的数据变成可用形状"时，方向永远是 **TDengine →（只读拉取 + 聚合）→ PostgreSQL**，绝不反向。
4. 回填、重算、补数这类动作，**目标库是 PostgreSQL**，源库只读。

## 后果

- 回填类脚本必须能被一眼看出只读：不出现任何写 TDengine 的语句；评审时把这条当硬门。
- 引入 TDengine 客户端的地方，使用**只读**连接/账号；不要给它写权限。
- 原始序列的权威只有一处（TDengine），所以"PG 里的行数对不上 TDengine"是**正常现象**，不是数据丢失——判据要对"应该聚合出多少小时行"，而不是对原始行数。
- 若将来确需在 TDengine 侧建库表（例如新增设备表），那是**采集侧的变更**，必须单独提案，不在本 ADR 的授权范围内。
