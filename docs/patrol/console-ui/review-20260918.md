# 巡检台界面问题分析与优化方案

- **评审对象**：`web/console/index.html`（1462 行，唯一页面）＋ `/api/preview/status` 数据面
- **评审日期**：2026-09-18
- **评审方式**：通读源码逐条核对"代码 ↔ 视觉/交互后果"，全部问题附行号，可逐条验收
- **已知上下文**：预览已于 09-18 提质到 1280×15@q7（约 7.2 Mbps，实测 14.6 fps）；抓拍电平修正已上机。本次评审独立于这两项。

---

## 结论摘要

页面骨架是好的（三栏工作台、急停常驻、失败帧说人话、空态文案都到位），问题集中在 **四类**：

1. **视觉一致性**：浅色主题是后来"盖"在暗色主题上的（CSS 里 `:root` 定义了两遍），一批硬编码暗色被漏掉——**生长曲线图、缩略图底板、日志分隔线、进度条底槽在浅色界面里是深色补丁**。其中 `drawCurve()` 整段图表色值是暗色主题遗留，是最显眼的一处。
2. **文案 ↔ 行为矛盾**：按钮承诺的快捷键/切换行为与实际实现不符（急停 Esc、看画面按钮最容易在现场"骗人"）。
3. **无障碍噪音与焦点顺序**：`.readouts` 容器每秒刷新且带 `aria-live`，读屏会持续播报；历史模式用 CSS `grid-row` 重排，DOM 顺序 ≠ 视觉顺序，Tab 焦点与大纲顺序错位。
4. **性能**：导轨图每 1 秒（指令执行时每 300ms）全量 `innerHTML` 重建并重新绑定事件，低端机上"边挪边看"会卡。

## P0 — 视觉一致性 bug（现场一眼可见，建议随下次发版修掉）

### P0-1 生长曲线图是浅色界面里的一块"暗色补丁"

`drawCurve()`（第 1325-1338 行）硬编码了暗色主题色值：

| 元素 | 现值 | 问题 |
|---|---|---|
| 坐标轴 | `#2a3340` | 深灰画在白卡片上 |
| 刻度文字 | `#8b98a5` | 中灰，对比度不足 |
| 长度曲线 | `#58a6ff` | 旧 `--accent`（暗色主题），浅色主题 accent 已是 `#1f6feb` |
| 伞盖曲线 | `#7ee2a8` | 浅绿画在白底上，辨识度低 |

对照：同页的导轨图 `drawMap()`（第 615-697 行）已经全部改为内联浅色值（`#6b7785`/`#c7d2da`）——曲线是漏改的一个。

**修法**：删除硬编码色，改用 CSS 变量或与浅色主题一致的固定值：

```js
// 长度 / 伞盖两条线分别用 var(--accent)/var(--ok) 语义色，轴与刻度用 var(--dim)
stroke="var(--accent)"  // #1f6feb
stroke="var(--ok)"      // #18794e
```

### P0-2 遗留的暗色 CSS 硬编码（未变量化部分）

第 8-113 行是旧的暗色主题块，第 115 行起又用一整套规则覆盖成浅色主题。凡是**硬编码颜色、且没被第二遍覆盖**的规则全部残留：

| 位置 | 规则 | 现场观感 |
|---|---|---|
| 34-35 行 | `.im{background:#0e1319}` / `.im img{background:#0e1319}` | 历史缩略图是深灰方块，与白卡片断层 |
| 44 行 | `#log div{border-bottom:1px solid #202834}` | 事件日志分隔线是深色 |
| 46 行 | `.bar{background:#0e1319}` | 巡检进度条底槽深色 |

**修法**：把这三处换成 `var(--soft)`/`var(--line)`，然后**整段删除第 7-113 行的暗色块**（`:root`、`.pill.*` 之外它还在重复定义 button/input/viewer 等十余条规则，两遍定义并存是维护陷阱）。

### P0-3 "急停（Esc）"的承诺与实现矛盾

按钮文案写死"急停（Esc）"（第 297 行），但 Esc 处理是 `e.key === 'Escape' && busy()`（第 1082 行）——**空闲时按 Esc 没有任何反应**。这是刻意设计（注释 1080-1081 行：避免误触闩锁），但按钮文案不知道这件事。现场试一次没反应，大概率去拍硬件急停，或者以为页面卡死。

**修法（二选一）**：
- 按钮改为"急停"，`title="执行中可按 Esc 中断；空闲时请直接点此按钮"`；或
- 保留"（Esc）"但在空闲时给一次明确的视觉反馈（如按钮震颤 + 提示"当前没有执行中的指令"）。

### P0-4 "看画面"按钮不反映状态

`#pvbtn` 文案恒定为"看画面"（第 237 行、1186 行），打开后也不变成"关闭画面"。现场要从卡片右上角的"播放中/未打开"小标签反推按钮作用。

**修法**：进入 `pvStartStream/pvStopStream` 时同步改按钮文案（"关闭画面"/"看画面"）。

### P0-5 抓拍置灰没有可见理由

`capbtn` 在 `!selected` 时禁用（第 912 行），原因只写在 `title` 里，鼠标不悬停看不到。现场最常见的疑问就是"为什么抓拍点不动"。

**修法**：disable 时在按钮下方（`#pverr` 位置或 `.m` 里）常驻一行小字"先选站位 → 抓拍可用"；选中后消失。

## P1 — 可访问性与性能（影响现场实操手感）

### P1-1 读屏会持续被 `.readouts` 骚扰

`.readouts` 容器带 `aria-live="polite"`（第 241 行），而里面的"当前位置/目标站位/直线距离/当前动作"每秒（执行中 300ms）刷新——读屏软件会把每一个变化都念出来。

**修法**：容器去掉 `aria-live`；对"当前动作"这种真正需要播报的状态用一个独立的 `aria-live="polite"` 小节点，且只在**文本变化时**写入（不是每次刷新都写）。

### P1-2 历史模式 DOM 顺序 ≠ 视觉顺序

第 173-177 行用 `grid-row` 把 timeline/大图/曲线三张卡重排（大图视觉第一、DOM 第二）。后果：Tab 焦点在大图之前先经过时间轴，读屏的大纲顺序也和眼睛看到的相反。

**修法**：直接调整 HTML 里三张卡的 DOM 顺序为大图→时间轴→曲线，删掉 175-177 的 `grid-row` 规则。

### P1-3 导轨图每秒全量重建（性能）

`tick()` 1 秒调一次 `drawMap()`（第 861 行），busy 时 `applyCommandState` 再以 300ms 节奏调（第 1009 行）。`drawMap` 是整段 `innerHTML` 拼接 + 重建后重新 `querySelectorAll('.map-station')` 绑事件（第 692-696 行）——每次重绘都重建几十个 SVG 节点并重新绑定。滑台持续移动时，中栏地图跟随会明显消耗主线程。

**修法**：拆成静态层与动态层两层 `<g>`——层带/网格/列层号/蛇形路径/站位点只在数据变化时画；当前十字（686-691 行）、目标虚线、pending 方框（673-678 行）放进动态 `<g>`，每帧只更新它们的 `cx/cy/x1...` 属性。事件监听绑在外层 SVG 上（现在站点点击本就走的是命中圈计算 `mapStationAt`，改造后仍用同一函数，逻辑不变）。

### P1-4 `/api/images` 两份重复实现

`selectStation()`（758-792 行）和 `loadHistory()`（1358-1375 行）几乎重复地加载同一接口、各写一套缓存与竞态处理（`stationRequestSeq` / `historyRequestSeq`）。行为漂移风险（比如一处加了 `prod_error` 提示另一处没有）。

**修法**：抽一个 `loadStationImages(id, {force})`，两边共用；实时模式渲染成网格、历史模式渲染成时间轴，只分展示不分数据获取。

### P1-5 页面不可见仍在轮询

1 秒 `/api/status` + 2 秒 `/api/preview/status` 不管 tab 是否可见都跑（第 1458、1173 行）。现场多开几个标签就是成倍请求。

**修法**：`document.addEventListener('visibilitychange')` 隐藏时清掉定时器、恢复时补一次立即 `tick()`。急停是按钮动作，不依赖轮询，隐藏期间不影响安全。

### P1-6 实时画面没有质量仪表

`/healthz` 已经给出 `frames / viewers / last_frame_age_s / uptime_s`（preview.py:167-176），页面只用了 `last_frame_age_s`。刚做完的提质（1280×15、7.2 Mbps）现在**在界面上无从证明**——现场再说"糊"时无法当场自证。

**修法（两小步）**：
- `preview.py` 的 `status()` 增加窗口帧率估计（保留最近 5 s 的帧时间戳，算 `fps_recent`；帧数重连清零时归零）；
- 页面在实时画面卡片的 `#pvnote` 位置显示：`1280×15 · 14.6 fps · ~7.2 Mbps · 1 名观众`（码率可按 `frames × 平均帧字节 / 窗口` 估算，后端给公式前端只读数）。

P0×5、P1×6、P2 的 2/3/4/5/6 已全部实施并通过回归（`verify-page.js` 125/125，无运行期错误）；

无头截图复验时新抓到一个**实施引入的布局 bug**（原评审未覆盖，记在这里备查）：

- **现象**：历史模式大图卡的"帧导航"和"1×/2×/4×/适应"缩放按钮看不见；时间轴缩略图、曲线表格也被裁。
- **根因**：`#hmain` 用 `grid-template-rows:minmax(300px,1.25fr) minmax(150px,.55fr) minmax(150px,.7fr)` 固定比例行高，卡片 `overflow:auto` 各自内滚。1080p/1200px 窗口下三张卡的行高（约 303/455/200px）都装不下内容，新加的帧导航行被折进大图卡的折叠区。
- **修法**：`#hmain` 退回普通块级堆叠（删掉 grid 行定义与卡片级 `overflow:auto`），由 `#hmain` 整列统一滚；`.viewer` 去掉 `height:100%`（auto 行高下无可解析参照），保留 `min-height:260px`，图来了按原始宽高比撑开。
- **教训**：`grid-template-rows:auto` 也不行——`align-content` 会把 auto 行拉伸成等高，一样裁。固定比例行高 + 卡片内滚这套组合，任何"往卡片里加一行"的改动都会把它折掉。
- **验证方式**：Chrome 无头 + 注入探针读 `getBoundingClientRect`/`scrollHeight`，确认三卡 `scrollHeight ≤ 卡片高`、帧导航落在大图卡内；再截整页图目视确认。

## 修订记录（2026-09-21 同日，现场反馈）

P2-1 发到现场后收到两条反馈，当天修订；两条都不改架构，只改"说什么"和"什么时候能拍"。

### 修订一：摘要去掉帧数（现场问"总帧数是干嘛的"）

**反馈原话**：实时显示总帧数的目的是什么？这里不需要累积或者存储中间帧。

现场说得对，而且**两处都错**（页面上的实时画面状态行 + P2-1 的站位摘要）：

- **实时画面状态行**原本显示 `~14 fps · 42 帧 · 1 名观众 · 最新一帧 0.4 秒前`。那个 `42 帧` 是
  上游 `Broadcaster` 的累计计数，只增不减、重连还清零，页面拿它**只做 fps 差值**。把一个纯内部
  中间量摆出来，等于暗示"系统在攒 N 帧"——而实时链路**恰恰不保存历史**（`preview.Broadcaster`
  只留最后一帧给新连上的观众）。判"流健不健康"看 fps 与帧龄就够了。**已删**，`frames` 退回纯差值输入。
- **站位摘要**原本报 `末帧 MM-DD HH:MM · N 帧` 与 `⚠ N 帧失败`。这里的 `N` 是 `images(limit=2000)`
  **截断窗口内**数到的行数，不是这一站拍过多少——某站历史一多就被别的站挤出窗口，读出来比不给更糟
  （典型的"看起来精确、实际有偏"）。而且这条线上要判的只有"最近一次拍成了没有、是什么时候"。
  **已删两项**，只留 `末帧 MM-DD HH:MM` 与 `⚠ 末帧失败` 角标；后端 `station_summary()` 改为逐站
  取**首行**（行集合按 ts 倒序）而不是聚合计数，函数反而更短。

**教训**：聚合窗口的计数天然有偏，凡"窗口内计数"都不要当总量报；只报**可行动**的信号
（末帧时间、末帧成没成）比分位数字更有用。

### 修订二：非格点也要能抓拍

**反馈原话**：非设定的格点也会存在抓拍需求，当前是不能抓拍的。

根因在**前端**：`#capbtn` 被 `locked || !selected` 置灰，`onclick` 里还有一道"先在左栏选一个站位"
的早退。抓拍链路本身不要求站位——`manual_exec._capture` 先 `fmc.current_yz()` 读实际位置再拍，
`station_id` 只决定"这张照片以后挂在哪一站的历史下"。

**改法（归属口径 = 用户选的"归到最近的格点"）**：

- 新增 `patrol.stations.nearest_station(stations, y, z)`：距离按**格距归一化**后再比
  （`((y-sy)/y_pitch)² + ((z-sz)/z_pitch)²`），不是直接比毫米。直接比欧氏距离的话 Y 的 374mm
  格距会完全盖住 Z 的 42mm 格距，把"上一层"的点判给同一层的站位（测试
  `test_nearest_compares_in_grid_units_not_raw_millimetres` 钉死了这个分歧）。
- `manual_exec._station_for(cmd, *, y, z)` 改成返回 `(station, auto)`：显式给了站位按它；

### 修订三：真机复验抓到的一处"死预告"（同日，发版后）

前两条上机后（镜像 `0.1.0-20260921151249-39aacfe`）用无头浏览器打现场 URL 取渲染后的
DOM 复核，发现 `#capnote` 是**空的**：

- **根因**：`posNow()` 读的是 `lastStatus.machine.real_pos`，而 `console.status()` 里
  `connected` 的定义就是 `source == "controller"`，`source` 只有 `station`（巡检中由
  当前站位推出）或 `none` 两种取值 —— 也就是说 **console 从不主动连控制器**
  （ADR-0004/0013：单会话设备，只有执行方碰它）。现场实测 `real_pos: null`、
  `pos_source: "none"`。所以"位置读不到"是**常态**，而早先的写法写成了
  `if(!selected && near) ... else if(!selected && p) ... else 留空`，
  在这条常态下整句留空 —— 预告是死的。
- **它为什么该被当成缺陷**：这正是同一个毛病的第二次出现（第一次是"实时显示总帧数"）——
  UI 上摆了一个**在真实运行条件下不产生任何输出**的元素。单元测试与 jsdom 用例都测不出来，
  因为假后端**总是**给 `real_pos`（假件的默认值比现场"更好"）。
- **修法**：不拿"最后成功目标"去猜站名（抓拍前机构可能已被别处挪过，猜错比不猜更坏——
  告诉他归 S102、结果写成 S101），改为**分三档说清规则**：
  选中站位 → 留空（按选的走）；位置+站位表都有 → 给具体站名与 ΔY/ΔZ；
  只有位置 → 只说规则；**位置读不到 → "拍照后按实际位置归到最近的格点（归到哪一站写在
  下方结果里）"**。末档是现场常态，必须非空。
- **顺带记一条假件纪律**：假 `/api/status` 的 `real_pos`/`pos_source` 应当能把**现场真实
  取值**（`null` / `"none"`）也覆盖到，否则"读不到位置"这条路径永远测不到。
  `verify-page.js` 已补一条断言钉住它。

### 修订四：抓拍被误关进"要会话"的名单（现场反馈"打开画面点抓拍没反应"）

**反馈原话**：在零点打开画面，点击抓拍，没有反应。

**取证**（prod 只读）：`/api/cmd` → `session_active: false`、`estop: false`、无在飞指令；
`/api/cmd` 的最近结果是 **13:05 的 `home`**（"回零完成…Y=0.00 Z=0.00"，即"在零点"）——
**没有任何 `capture` 指令进过队列**。也就是说点了之后后端根本没收到，不是"收到了没执行"。

**根因**：页面把抓拍和运动按钮共用了一份门槛：

```js
const locked = est || !active || busy() || inRound();   // active = session_active
$('#capbtn').disabled = locked;                          // ← 抓拍被 !active 一起关掉
```

而**抓拍不需要会话**：会话只约束运动指令（`MOTION_KINDS = ("goto","jog","home")`，
`ManualChannel.submit` 只对它们校验有效会话；`manual_exec.py` 里 `session` 出现 **0 次**），
ADR-0016 §6 也明写"手动抓拍不移动机构"。spec §6 里那句"任何一条**运动命令**都续期"就是
会话的作用范围。

**为什么表现成"没有反应"**：`disabled` 的按钮**连 `click` 都不派发**，`onclick` 不执行、
后端也收不到、页面也没有任何提示。这是"点了没反应"的完整解释——它不是"请求失败了"，
而是"请求从未发生"。

**改法**：`#capbtn` 单独算门槛 `est || busy() || inRound()`（去掉 `!active`，与后端
的三种 409 逐条对应），并让 `#capnote` **先解释为什么不能拍**（急停 / 巡检中 / 上一条没结束），
没被锁时才说归属规则。三档与后端拒绝理由一一对应，写进 spec §6.2 的表里。

**测试**：`verify-page.js` 148→155，新增 6a（未接管时抓拍可用、且能真发出去）与 6b
（三种置灰必须说原因）。同时**改掉一条把错行为写死的旧断言**：
`未接管时点动/定位/回零/抓拍都禁用` → 拆成"运动类禁用"+"抓拍可用"。

**为什么本地全绿却在现场中招**（同一个毛病的第三次）：用例在前面就 `takebtn` 过，
会话一直有效，`!active` 那条分支**从没被走到**——假件的默认状态比现场"更好"。

### 复验时发现、**未修**的一条（留给产品决定）

页面**没有"取消选择站位"**：`selected` 只在 `selectStation()` 里被赋值，没有任何地方
把它置回 `null`（地图空白处点击是"填坐标"，不是取消选择）。后果是：一旦点过任一站，
之后每一枪抓拍都会**归到那一站名下**（`sendCmd('capture', selected ? {station_id:selected} : {})`），
"按位置归到最近格点"这条路就再也走不到了（除非刷新页面）。

不是静默错误——结果 detail 会写"已拍 S101（拍摄位置 Y=… Z=…，偏离 S101 格点 ΔY=…）"，
偏了看得见。但"选过就回不去"对刚上线的非格点抓拍是个实打实的坑，建议补一个取消入口
（取消后 `#capnote` 回到归属预告）。修法是页面-only，不需要重建镜像。
