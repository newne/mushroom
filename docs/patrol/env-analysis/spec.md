# 环境参数分析界面设计规格

来源：2026-10-12 用户要求"查询当前批次的环境参数，制作环境参数分析界面，后续能够结合拍照识别的生长情况和基本参数进行自动化调整"。

修订记录（2026-10-12，同日三次）：

1. 初版：以实测环境四维为分析对象。
2. 第二次：用户要求"更应该关注每天的调整参数"，主体一度移到设定。
3. **第三次：用户澄清"实际应注意每天、每小时库房温湿度/CO₂/光照的参数……本模块的目的是充分学习各生长阶段、长势背景下库房的调整方式；因此变更本身需要记录分析，但重点还是实际参数"。主体回到实际参数，变更记录作为"调整方式"的载体保留。见 §2.1 与 ADR-0022。**

4. **第四次（现行，2026-10-23）：取消 10-22 的两个子窗口。操作维度（每次调节 × 当时蘑菇图像 ×
   调节前后环境）必须与日分布同屏可见——那是上一版就有的功能；逐天明细表删除，
   日分布图已按天画全，表只是重复。**

## 1. 目标与边界

**模块目的**：充分学习各生长阶段、长势背景下，库房的调整方式。

**主对象**：实际参数，即每小时（并按天汇总）的库房温度、湿度、CO₂、光照。
**副对象**：设定变更记录。运行巡检人员按生长状态与温度变化定时调整运行参数，这些变更必须记录、必须分析，是"调整方式"的唯一载体，但不占主体。
**分层维度**：生长阶段（D 分档，另可切图像 4 阶段）× 长势（生长速率、测量长度）。

**本期做**

- 巡检台新增「环境」模式：小时级实际参数曲线为主线，变更标记与变更表解释曲线为什么拐弯，可按生长阶段切片看。
- 实际参数与变更记录的数据链路单源化（ADR-0021、ADR-0022）。
- 区间表出两张：**实际参数区间**（主）与**设定区间**（次）。

**本期不做**

- 不下发、不闭环。沿用 `fmc4030-camera-scan/spec.md` §6「本期只建议不闭环」。今天仓库里不存在写回能力：`GetData.write_instruction` 零调用者，`decision_analysis_dynamic_result` 的 `apply_time`/`apply_result`/`rollback` 三列从没被写过，`decision_analysis_batch_status.status` 只有记录、没有代码响应。
- 不新增第二套建议逻辑。界面上的建议一律来自既有 `decision_analysis` 输出。
- 不采购照度传感器（列入现场建议单）。

## 2. 数据口径

### 2.1 四个角色

| 角色 | 是什么 | 回答的问题 | 在界面上的位置 |
| --- | --- | --- | --- |
| **实际参数**（主） | 每小时实测温度、湿度、CO₂、补光时长，及日汇总 | "库房实际是什么状态" | 曲线区主线 |
| **调整动作**（次，必须有） | 操作日志：谁、何时、把哪个点位从什么改到什么（环控平台命令审计） | "怎么调的" | 操作记录表 + 时间轴标记 |
| **生长阶段与长势** | D 分档（或图像 4 阶段）× 生长速率 / 测量长度 | "在什么背景下调的" | 分层切片 |
| **产量** | 批次鲜菇总产量 | "结果如何" | 区间表的验证列 |

分析与展示以实际参数为主体。变更记录不替代实际参数，它解释实际参数：巡检人员根据生长状态与温度变化定时调整设定，实际参数是这些调整落地后的结果。

### 2.2 实际参数（四维）

| 维度 | 变量 | 来源 |
| --- | --- | --- |
| 温度 | `temp_c` | 面板 `TD1_Q{1..4}MDTM01::Tatmosp` |
| 湿度 | `rh_pct` | 同设备 `Hatmosp` |
| CO₂ | `co2_ppm` | 同设备 `Co2` |
| 光照 | `lamp_on_m` / `lamp_off_m` + `lamp_blue_groups` / `lamp_white_groups` | 补光灯的**设定**：循环周期与四组光源选择（`Choose1..4`），**不是 lux、也不是实测点亮时长** |

`zone` 一律存库房号（611/612/607/608）。`light_lux` 列保留给将来的照度传感器，无源期间一律 NULL，界面标注"无数据源"，不许显示成 0。

**2026-10-22 口径修订（补光）**：

- `OnSSet`/`OffSSet` 现场取不到值 ⇒ **补光只看设定**（`OnMSet`/`OffMSet`），
  **不折算启停时间、不算占空比、不展示"点亮分钟"**。`lamp_on_min` 列保留给区间表等
  下游派生，但页面不再作为读数。
- 补光要**区分补蓝光与补白光**：`Choose1..4` = 0 白光 / 1 蓝光，`OnOff1..4` = 1 自动 /
  0 关闭；两者一起折成 `lamp_blue_groups` / `lamp_white_groups`（组号清单，如 `"2,4"`）。
  `null` = 这一窗口没上报过光源选择，`""` = 这一档没有组（如四组全选白光）——两者在界面上分开显示。

**入库首日（D0）**：设备刚启动，环境参数还在往稳定态走。**统计口径默认跳过 D0**
（KPI、窗口统计、操作经验汇总从 D1 起算）；图上与逐天表里 D0 仍然列出并标灰，
数据是真的、只是不参与统计。可在页面上取消勾选。

### 2.3 时间粒度与落库口径

- **小时**是分析与落库的粒度：同一小时的采样折成一条聚合行——每参数的 mean/min/max、补光状态众数、采样点数 `n`。
- **天**在读取时由小时行再折一层（均值按采样点数加权，断档的小时不会把日均值拽偏）。
- **原始分钟序列不落库**（2026-10-12 定，ADR-0023）：TDengine 才是它的权威，需要时按窗口现取 `GET /environment?granularity=raw`，上限 6 小时。
- `n` 让断档可审计：不足 60 就是该小时有缺口，不补、不插值。
- 口径分界：`min/max` 是**采样点级别**的真实极值，`q25/median/q75` 是"每小时一个点"的分位数。两者不是同一个粒度，别混读。

### 2.4 调整动作的登记（操作日志）

**权威来源是环控平台的命令审计**（2026-10-12 用户给定）：
`POST /service/monitor/command/audit/log/page/list`，登录在 `POST /service/security/auth/login`
（口令要 MD5），业务接口带 `X-AUTH-TOKEN`。一行一次操作，字段：
`operator` / `operateTime` / `deviceName` / `pointName` / `pointValue` /
`actionSource`（现场/远程）/ `actionContent`（"加湿开启设定[5]"）。

**这类记录逐条留，不聚合**：一天几十条，事件本身就是最小有意义的单位——聚合成
"每天改了几次"之后就答不出"那天 10:10 谁把右加湿器的开启设定改成了 5"，
而那句话正是要学的经验。与实测数据的分界：实测是每分钟一条的连续量，只留小时聚合；
操作是稀疏事件，逐条留（ADR-0023 补记）。

`device_setpoint_changes`（每小时差分检出）是**旧路径**，可以留着做交叉验证，
但不再是权威——审计日志有操作人与动作来源，差分只有值的变化。

`device_setpoint_changes` 已经在记这件事：每小时第 5 分钟的 `hourly_setpoint_monitoring` 按 `decision_analysis_static_config` 的点位表查询环控历史，检出变更后写一行（`room_id`、`device_type`、`device_name`、`point_name`、`change_time`、`previous_value`、`current_value`、`in_date`、`growth_day`、`in_num`、`batch_id`、`change_type`）。

**进分析的参数集直接取 `src/configs/monitoring_points_config.json` 的点位表**，不另立一份。那张表覆盖的正是巡检人员会调的东西：冷风机的 `TemSet/TemDiffSet/CycOnTime/CycOffTime/CycOnOff/ArOnOff/HumOnOff`、新风机的 `Control/Co2On/Co2Off/On/Off/Model`、加湿器的 `On/Off/Model`（HUM01/HUM02 两台）、补光灯的 `Model/OnMSet/OffMSet/OnSSet/OffSSet/OnOff1..4/Choose1..4`。

变更记录在界面上有两种用法：单条事件标在时间轴上（解释拐点），以及按生长阶段汇总出"这个阶段通常怎么调"（频次与幅度，`setpoint_analytics` 的 `avg_magnitude` 可复用）。

### 2.5 每日设定末态

一天之内一个点位可能被改多次，而"当时运行在什么设定上"只有一个答案。规则：按（批次, 生长天数, 设备, 点位）取当日最后一次变更的 `current_value`；当天没有变更就沿用前一日末态；批次首日前无末态则标"未知"，不猜。它是变更事件与设定区间之间的桥：事件说明"改了"，末态说明"改成了什么，然后一直是那个值"。

### 2.6 批次身份

权威 =（库房号, 入库日期）。库房号取 `mo_gu_batch.code_num`，入库日期取 `in_time` 的日期部分；面板 `TD1_Q{1..4}MDINFO01` 的 `InYear/InMonth/InDay` 作**交叉校验**，不一致时告警并在界面双显（ADR-0020）。三种字符串写法都是派生显示名：

| 写法 | 出处 |
| --- | --- |
| `mogu-<mo_gu_batch.id>` | 巡检侧 `batch_no`，`deploy-fetch-room` 已落盘 |
| `<room_id>_<%Y%m%d>` | 算法侧 `device_setpoint_changes.batch_id` |
| `<room_id>|<in_date>` | Streamlit 看板 `batch_key` |

「当前批次」= 该库房最近一条入库日期不晚于今天的批次。

### 2.7 生长与长势

- 生长阶段主键 = 生长天数分档 `D1-D7 / D8-D14 / D15-D21 / D22-D28 / D29+`，与 `control_ops_dashboard/data.py:211` 同源；图像识别的 4 阶段（Substrate / Primordia / Fruiting / Post-harvest）作可切换的第二种切片，缺就留空。
- 生长天数两套口径并列显示：我们的第 N 天（入库当天 = 0）与生产系统口径（入库当天 = 01）；面板 `INFO01::InDayNum` 作第三个数校验。
- 长势 = 生长速率与测量长度（`mean_len_mm` / `mean_cap_mm`），作阶段内的连续分层维度。

### 2.8 最终产量

= 该批次全部 `mushroom_batch_yield` 行的 `fresh_weight` 求和（鲜菇，单位斤）。缺行即"缺失"，**不许当 0**。产量只作区间表的验证列，不作优化目标。这与 `decision_prompt.jinja:47`"产量/品质数据仅用于回溯分析，不参与当前调控决策"的既有约定一致。

## 3. 界面（巡检台「环境」模式）

页面没有路由层，模式是 `#modeSeg` 的按钮加 `setMode()` 里的分支。环境模式与「实时 / 历史」同级，三栏沿用现有栅格。

**环境模式是一页两块（2026-10-23 用户口径，取消 10-22 的子窗口）**：两块同屏可见，共用一次
取数（`loadEnv`）。操作维度不能藏在第二个窗口里——用户要的是"补回上一版就有的、每次操作
前后的蘑菇图像"，翻页签等于没有。

| 区块 | 回答的问题 | 内容 |
| --- | --- | --- |
| **本批次时序（逐天）** | 环境怎么走的 | KPI（跳过 D0）· 日分布图 · 窗口统计 · 补光设定（蓝光/白光分组）· 批次对比 · 断档 |
| **操作维度** | 人为什么这么动它、动完怎么变 | 操作会话 × 相邻轮次三联图（每帧带当时温湿 CO₂）· 每次会话的**调节前/后 3 小时环境对照** · 原始操作记录 · **操作员调控经验**汇总 |

**中栏（2026-10-21 改：日分布为主视图，ADR-0027）**

- **日分布视图**：横轴 = 生长天数（本批全量、缺天不补、停采后轴截断），温 / 湿 / CO₂ **各一张图**，
  每张图里三层共用一个纵轴：
  1. **日箱线**（小时口径）：一天 24 个小时均值的 q1 / 中位 / q3 + 须；
  2. **中位数折线**：跨天相连，看清趋势；
  3. **小时均值曲线**：与箱线同图同轴，箱体里的样本就是这些点；
  4. **采样点级极值带**：淡色 min–max 范围带（来自 `*_min`/`*_max` 列），图注标明它与箱线不是同一粒度。
  **不画双纵轴**（同量纲双轴会自己骗人）。
- **补光设定带**：光照**不做箱线**，按补光设定的变化点（`OnMSet`/`OffMSet` 与蓝光/白光组）
  切段，画一条横跨同一横轴的色带；悬停给出"蓝 x# / 白 y#"。
- **操作 × 长势卡**（见 §3.1）：左列操作会话时间线，右列选中会话的三联对照图。
  它是环境页的**下半块**，与日分布同屏，不再收进子窗口。
- **变更标记**：设定变更在时间轴上的竖线或点，悬停显示"点位 从 → 到"；密集时段折叠成计数
- **阶段切片**：按 D 分档或图像 4 阶段切换时间窗
- 区间参考带（来自区间表）：**本期不叠在箱线上**——`/ranges` 常态为 `no_measurements`，叠上去只会多一块"因为算法没跑所以什么都没有"的空白。区间表仍在批次对比卡里按其七态各自具名显示。

**72 小时小时曲线**：不再是独立视图。日分布图里的小时均值曲线承载小时级信息；需要看夜间短时细节时走历史模式的节点放大（那里另有一条环境带）。

### 3.1 操作 × 长势（ADR-0028）

目的：把「人在什么长势下做了什么调节、调完之后长势怎么变」摆在同一屏。

- **分析单元 = 操作会话**：同库房内相邻审计记录间隔 ≤ 10 分钟并入一次调节（`n=1` 也成立）。
  会话内保留逐条点位明细（设备 / 点位 / 值 / 操作人 / 动作来源）。
- **相邻巡检 = 相邻的巡检轮次**（约 3 小时一轮），不是 ±10 分钟窗口。
- **三联 = 同一观察框 × 最近 3 轮，且强制跨越会话时刻**（≥1 帧在会话前、≥1 帧在会话后）。
  凑不齐跨越 ⇒ 如实标"无后续巡检 / 无前置巡检"，不拿调节前的帧充数。
- **只给图、不给数值**：`measurements` 尚无 `round_id`，时间窗近邻 join 会把"没测"说成"没长"。
- **每帧带当时的环境值**：该帧时刻（或之前最近一小时）的温度 / 湿度 / CO₂，让"图像 ↔ 环境"
  在一行里对得上。
- **调节前/后环境对照**（2026-10-22）：会话前 3 小时与后 3 小时的小时行均值 + 差值，
  另带当时的补光设定（周期 + 蓝/白光组）。**只描述发生了什么，不推断因果**。
- **操作员调控经验**：按操作人汇总调节次数、常调点位、调后平均 Δ。默认排除入库首日
  （设备刚启动，那时的调节不算常规经验），页面注明排除了几次。
- 观察框默认 `B206`（第 2 层第 6 框），可换。

**右栏**

- **操作记录表**：谁、什么时候、把哪个设备的哪个点改成了什么（运行经验的原始记录），
  附按天/操作人的计数。"这段时间没人动过"与"取不到"必须分得开
- **设备面板表**：按设备分组列出面板关注的点位与当前值，分实测 / 设定 / 状态三类列；点位表由 `monitoring_points_config.json` 驱动，不硬编码
- 批次卡片：库房、入库日期、第几天（两套口径 + 面板 `InDayNum` 校验）、数据止于
- 断档与缺失清单
- 建议（只读）：既有 `decision_analysis` 输出的最近一次建议与依据

**空态**：无在库批次时明确说明"无在库批次，数据止于 X"，不画空图。

analysis 侧新增（`analysis/src/analysis/api.py` 的 `create_app` 内加闭包路由）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/environment?zone=&start=&end=&granularity=hour\|day` | 读库里的小时聚合（界面默认 hour） |
| GET | `/environment?…&granularity=raw` | **现取 TDengine** 的原始分钟序列；窗口上限 6 小时 |
| GET | `/environment/summary?zone=&start=&end=` | 每参数 min/median/max/q25/q75/count + 断档点 |

| GET | `/operations/sessions?zone=&start=&end=&entry_date=&window_min=10&box_id=B206&frames=3&limit=` | **操作会话 + 三联图像**（2026-10-21 加，ADR-0028）。只读 `operations`/`rounds`/`images`，不建表。`entry_date` 用于算 `growth_day`，不传则天数留 `null` |

2026-10-22：`/environment`（hour/day）与 `/environment/daily` 的每行新增
`lamp_blue_groups` / `lamp_white_groups`（组号清单文本，取自 `Choose1..4` 与 `OnOff1..4`）；
`/environment/summary` 的 `lamp` 段带 `blue_groups` / `white_groups`。
"跳过入库首日"是**页面把 summary 的 `start` 右移一天**，服务端不收额外参数、也不删数据。

落库：`environment_daily` 由 `analysis.env_daily.refresh(conn)` 重算，挂在每日任务上（`DAILY_AT` 环境变量装配到 `analysis.jobs`，与 `RANGES_AT`/`BATCH_AT` 同一套方式）。**没有封版**：每晚全量重算、按库房整删整写，迟到的小时行会改写旧批次的日行。

console 侧反代（照 `/api/growth` 的写法，保持单一 origin）：`/api/environment`、`/api/environment/summary`、`/api/environment/daily`、`/api/operations`、`/api/operations/sessions`、`/api/setpoints/daily`。

整列无源时返回 `null` 并在响应里标 `sources_missing`；空窗口返回空数组，不返回伪造的 0。

## 5. 区间表（`ranges`）

出两张，不要混在一张里：

**实际参数区间（主）**——按 D 分档（可切图像 4 阶段）× 长势分层，统计 `temp_c / rh_pct / co2_ppm / lamp_on_min` 的分布（median / q25 / q75 / n），并列该层的生长速率与最终产量验证列。回答"这个阶段、这个长势下，库房实际参数落在什么范围、结果如何"。

**设定区间（次）**——按同一分层统计设定值的分布，并汇总该层发生过的变更（频次、幅度、主要点位）。回答"这个背景下通常怎么调"。

两张表都要把 `refresh_ranges` 接进既有每日任务链。今天全仓库只有测试调用它，等于从没跑过。

## 6. 空态与断档规则

- 实际参数最后一条早于批次结束日 → 标"数据止于 X（该批已采完）"。
- 缺整点 → 断点，不插值。
- 参数整列无源 → 标"无数据源"，不给 0。
- 产量缺失 → 标"缺失"，不参与该批次的验证统计。
- 当日无变更 → 末态沿用前一日；批次首日前无末态 → 标"未知"。
- 某阶段没有任何变更记录 → 标"本阶段无调整"，不等于"没有数据"。
