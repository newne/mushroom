# ADR-0022：以实际参数为主体，变更记录承载"调整方式"

日期：2026-10-12
状态：建议（随 `docs/patrol/env-analysis/spec.md` 一起评审）
相关：`fmc4030-camera-scan/spec.md` §6、ADR-0020、ADR-0021

## 背景

区间表的全名是"最佳**控制参数**区间"，但 `align.py` 分箱的是**实测环境**（`temp_c / rh_pct / co2_ppm / light_lux`）。名字说的是控制量，算的是观测量，这个错位此前没人指出，因为没有第二个数据源可以对照。

2026-10-12 用户给出面板关注的 45 个点位，随后在一天内三次收紧口径：

1. 先要求"更应该关注每天的调整参数，直接代表操作员认为应该的运行方式"——本 ADR 的第一稿据此把分析主体定成了设定值。
2. 再澄清："实际应注意每天，每小时库房温湿度/CO₂/光照的参数，运行巡检人员会根据蘑菇的生长状态、温度变化定时调整运行参数；本模块的目的是充分学习各生长阶段、长势背景下，库房的调整方式；因此变更本身需要记录分析，但重点还是实际参数。"

第二稿（把主体放在设定值）是对第一句话的过度解读。主体是实际参数；变更是巡检人员的动作，必须记录与分析，但它服务于理解实际参数，不取代它。

仓库里这条链路的零件都现成：`device_setpoint_changes`（每小时检出变更并落库）、`decision_analysis_static_config`（点位登记表）、`control_strategy_kb_stage_rules.preferred_setpoint`（按生长天聚合出的推荐设定点）。缺的不是数据，是按"阶段 × 长势"把实际参数与调整动作摆在一起看。

## 决定

1. **主对象是实际参数**：小时级的温度、湿度、CO₂、补光时长，按天汇总。界面主线、区间表主表都是它。
2. **变更记录必须记录与分析**，它是"调整方式"的唯一载体。用法有两种：单条事件标在时间轴上解释曲线拐点；按生长阶段汇总出"这个阶段通常怎么调"。
3. **模块目的是学习各生长阶段、长势背景下的调整方式**。因此界面与区间表都要支持两种分层：生长阶段（D 分档，可切图像 4 阶段）× 长势（生长速率、测量长度）。
4. 区间表出两张：**实际参数区间**（主）与**设定区间**（次），按同一分层聚合，不混在一张里。
5. 每日设定末态按（批次, 生长天数, 设备, 点位）取当日最后一次变更的 `current_value`；当天无变更沿用前一日；批次首日前标"未知"。它是变更事件与设定区间之间的桥。

## 后果

- "最佳控制参数区间"这个名字仍然名不副实，主表从今天起正名为**实际参数区间**；设定区间只回答"通常怎么调"，不回答"该怎么设"。
- 界面以小时曲线为主线，变更是曲线上的标记而不是另一条主线。巡检人员看到的是"参数怎么走的、哪里被人动过"。
- 自动化调整的落点仍然在设定上（实际参数不可直接下发），所以闭环立项时要用的是设定区间那张次表，不是主表。这一点必须写清楚，否则将来会有人拿实际参数区间去下发。
- "长势"的分层阈值需要首批真实数据定标，本期先留可配置参数。
- 整套依赖 `device_setpoint_changes` 与实际参数的更新连续性。二者若同时停更（实际参数停在 `2026-04-09`），数据恢复前只有空态可显示。
