# ADR-0010：SDK 绑定必须声明 C 签名；运动等待必须越过「起转窗口」

日期：2026-09-13
状态：已接受并现场验证（prod `10.77.77.39`，控制器 `192.168.1.239:8088`）
相关：`docs/patrol/prod-deploy/motor-command-review.md`（F5/F9/F10）、`patrol/fmc/sdk.py`、
`patrol/fmc/client.py`、`docs/patrol/prod-deploy/m0-commission.py`

## 背景

在 prod 上第一次让轴真动时（`m0-commission.py --go`），连续撞上两个**长期潜伏、
只有真机运动才会暴露**的缺陷。此前所有成功调用（`Get_Machine_Status` /
`Get_Device_Para` / `Get_Version_Info`）都只用 `int` 与指针，恰好绕过了这两条路径，
所以单元测试全绿、文档也以为"命令复核完成"。

## 缺陷一：ctypes 没声明 `argtypes`，参数按错类型传

`loader.load_library()` 原来只是裸 `ctypes.CDLL(path)`。未声明 `argtypes` 时 ctypes
不会报错，而是按默认规则猜每个实参的 C 类型：Python `float` → C `double`（8 字节），
而厂商头文件里是 `float`（4 字节）。

- **症状**：`FMC4030_Jog_Single_Axis` 抛 `ArgumentError: argument 3`。
- **更危险的是不报错的情形**：参数从错位那一位起整体读成"另一个数"，而函数**照样返回成功**。
  对运动控制而言这是最坏的一类故障——机构走到别的地方，日志里全是 `rc=0`。

处理：新增 `patrol/fmc/sdk.py`，把 linux 版 `FMC4030.h` 的 24 个函数签名逐条落成表，
`load_library()` 加载后调用 `bind_lib()` 统一声明。指针参数用 `c_void_p`——它同时接受
`(c_ubyte*N)()` 数组与 `byref(struct)`，比 `POINTER(c_ubyte)` 宽容。

守护：`tests/test_fmc_sdk.py` 扫描全部 `self._lib.FMC4030_*` 调用点，**任何新增调用若忘记
登记签名就直接测试失败**；另断言运动类函数的形参声明为 `c_float`（不是 `c_double`）。

## 缺陷二：指令下发后的「起转窗口」内，状态字是上一条指令的残值

实测（Y 轴 `+200 mm @ 40 mm/s`，50 Hz 采样）：

| t | `Check_Axis_Is_Stop` | 状态字 `running` | 位置 |
| --- | --- | --- | --- |
| 0.001 s | **1（"已停"）** | 可能是 False | 未动 |
| 0.033 s | 0（运动中） | True | 起转 |
| 5.277 s | 1 | False | 到位 |

于是：

- `wait_stop` 在下发后**立刻返回"到位"（耗时 0.00 s）**。调用方以为到了，紧接着发下一条
  同轴指令——而 SDK 对未完成运动的 Jog/Line 是**静默丢弃**的（F5）。
- `wait_home` 更危险：`home_done` 的语义是"坐标系已建立"，**普通点动不会把它作废**
  （实测：Y 点动到 100 mm 后仍为 True）。回零刚下发时读到的 `home_done` 是**上一轮的**，
  据此返回会让调用方以为"已回到原点"而继续下发绝对坐标（整体偏移）。
  这个残值还解释了另一个现象：对仍在运动的轴下发回零会返回 **−10**（厂商表未收录，
  实测语义＝轴忙拒绝；而 Jog/Line 对同轴忙是静默丢弃——同一件事两种反馈）。

处理：两处等待都改成**两段式握手**，判据取状态字而非 `Check_Axis_Is_Stop`：

- `wait_stop`：只有**见过 `running`** 才认"已停"；一次都没见到起转（极短点动的整段运动
  可能落在两次轮询之间）则要求"已停"连续成立 `START_GRACE_S`（0.3 s）才算数。
- `wait_home`：先逐轴确认**起转**（`homing` 置起 **或** `home_done` 被清零——实测完整回零
  周期里两者都会发生，raw `0x0648 → 0x0681 → … → 0x0648`），再等 `homed`。
  起转窗口 `HOME_START_TIMEOUT_S`（3 s，实测起转发生在 22 ms）内没观察到起转即返回
  False（由调用方上报超时）——**绝不把"没确认"当成"成功"**。

守护：`tests/test_fmc_motion_race.py` 用照着实测时序写的假状态序列复现两种残值场景；
`tests/fmc_fakes.py` 同步补上回零过渡建模（不模拟它，这类竞态在测试里永远暴露不出来）。

## 现场验证结论

`m0-commission.py --go` 全流程通过（2026-09-13 00:48）：

| 步骤 | 结果 |
| --- | --- |
| Y 点动 +100 mm @ M0 档 | 10.10 s（理论 10 s） |
| Z 点动 −40 mm @ M0 档 | 10.15 s（理论 10 s） |
| Y 反向回零（从 +100 出发） | 3.62 s，落点 **Y=0.000** |
| Z 回零（从 −40 出发，当时用 `homeDir=1`） | 4.82 s，落点 **Z=0.000**（⚠️ 2026-09-15 更正：那次落的是**底部**，见 ADR-0018） |
| 首站 S101 `(187.17, −21.20)` | 到位 `(187.148, −21.200)`，偏差 ΔY −0.019 / ΔZ 0.000 mm |
| 单站采图 | HTTP 200、373 KB、`display: ":99"` |

## 后果

- **凡"下发运动 → 等结果 → 再下发"的模式，都必须走这两个握手**；直接读状态位判断
  "动作完成"在本控制器上是不成立的。
- 单元测试全绿**不能**证明 SDK 调用正确——必须在真机上至少完整跑一次运动链路。
  本次的教训写进技能 `.workbuddy/skills/fmc4030-field-verification/`。
- 厂商文档缺失的返回值（`−10`）按**实测语义**登记在 `fmc/errors.py`，并注明来源是实测
  而非手册；换控制器型号/固件时需重新确认。
