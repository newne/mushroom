# ADR-0017：实时预览用 RTSP→MJPEG 转码 + 同源代理（修订 spec §1 的"不做连续视频预览"）

日期：2026-09-15
状态：已接受
背景：`docs/patrol/console-ui/spec.md` §1 当初明确写了"不做连续视频预览（ADR 未立项，
`capture` 只有单次抓帧）"。现场用过之后提出：**手动接管时看不见画面**，点动/定位只能靠
坐标猜——而"把相机挪到那一框前面"这件事，眼睛比数字有用得多。

现场实测（2026-09-15，库房主机）：

| 事实 | 证据 |
| --- | --- |
| 采图服务**不能**当预览用 | 单次抓图 ≈5.2 s，且必然落一个文件（`storage=local/cloud`，没有"只回图不落盘"） |
| 相机**没有** HTTP MJPEG | `/ISAPI/Streaming/...` 全 404；服务自称 `H264DVR 1.0` |
| 相机**有** RTSP，且凭据可用 | 554 开着；用 `stations.yaml` 的 admin 凭据 Digest 认证，13 条常见路径全部 `200+SDP`（这台 DVR 不挑路径） |
| 相机**允许并发**会话 | 同时保持 3 路 DESCRIBE 全 200（预览占一路不会挤掉别人） |
| 页面**能**直接显示 MinIO 图 | `cloud_url` → 200、2880×1616 JPEG；但这与"实时"无关 |
| 宿主**没有** ffmpeg | 所以转码要放进我们自己的容器 |

## 决定

1. **预览 = RTSP 拉流 → ffmpeg 转 MJPEG → 同源代理 → 浏览器 `<img>`**。
   - 转码由**新的容器角色 `preview`** 承担（同一个巡检镜像、不同角色，沿用 ADR-0012 §4
     的"一个镜像多个角色"）：`ffmpeg -rtsp_transport tcp -i <rtsp> -vf scale=640:-2 -r 5
     -f image2pipe -c:v mjpeg -`，再把帧用 `multipart/x-mixed-replace` 广播给浏览器。
   - 分辨率/帧率默认 **640 宽 @ 5 fps**（够看清"对着哪儿"，CPU 与带宽都可控；这台 DVR 不挑
     路径、选不了子码流，所以只能解主码流再缩放）。
2. **浏览器只连 console**：页面用 `<img src="/api/preview">`，console 反代到预览容器。
   相机地址与凭据**不出现在任何浏览器可见的配置里**（与 ADR-0003 的单一 origin 一致）。
3. **只在接管时开**：预览不是常驻服务。页面在"接管"后自动打开、放开时关掉；一次只服务
   少量观看者（服务端广播，慢客户端丢帧而不是拖住所有人）。
4. **巡检进行中拒绝预览**（409 + 预计可用时间，复用 ADR-0013 的话术）：那一轮要用相机抓 60 张，
   尽管实测并发够用，也不去赌"两路同时拉流时抓图不受影响"。
5. **凭据只有一个来源**：`stations.yaml` 的 `camera_user`/`camera_pwd`（预览容器只读挂载它），
   与抓拍用的是同一份；URL 里的口令在任何日志里都要打码。

## 决定理由

- 现场提出的需求是"接管时要能看见画面"，而采图服务 5 秒一张的节奏对"边挪边看"没有意义；
  RTSP 是相机本来就有的能力，不需要动厂商 SDK 会话（那一路归采图服务）。
- 用 MJPEG 而不是 HLS/WebRTC：`<img>` 原生支持 `multipart/x-mixed-replace`，页面**零 JS 播放器、
  零 vendor 依赖**（spec §8 的"零构建"约束仍然成立），延迟 <1 s；代价是带宽比 H.264 高，
  但 640×360@5fps 在内网约 1–2 Mbps，可接受。
- 放在**同一个镜像的另一个容器**而不是塞进 `mushroom_patrol`：ffmpeg 崩了只重启预览，
  控制器那边不受影响；也不给控制面镜像增加转码这种无关负担（代价是镜像多约 150 MB）。

## 后果

- 巡检镜像多一个 `preview` 角色与 ffmpeg 依赖（`docker/Dockerfile.patrol` 里显式注明）；
  compose 多一个 `mushroom_preview` 服务（同镜像、`profiles: ["patrol"]`）。
- **相机并发**：预览占一路 RTSP。实测这台 DVR 允许 ≥3 路，但现场若换相机/换固件需重测
  （`docs/patrol/prod-deploy/probe-rtsp.py` 与并发探测脚本可直接复跑）。
- 老系统整点抓 6 台走的是 8000 端口的 SDK，与本方案不冲突；但**同一时刻**预览 + 抓图 + 老系统
  三方并发没有做过长时间实测，属于一期已知边界。
- 预览画面**不留存、不进历史**：它是"看一眼"，照片仍然只有一次性的「抓拍」会落索引与 MinIO。

## 落地形态（2026-09-15 实现，供对照）

| 位置 | 内容 |
| --- | --- |
| `deploy/preview.py` | 容器角色：帧切分 / 广播（队列 3，慢客户端丢帧）/ ffmpeg 监督（1·2·5·10 s 退避）/ `create_app`（`/healthz`、`/stream.mjpg`、`/frame.jpg`）/ `main()`（`--rtsp/--stations/--port/--scale/--fps`） |
| `deploy/console.py` | `GET /api/preview`（MJPEG 反代）、`/api/preview/status`（能不能看 + 上游健康，**永不 500**）、`/api/preview/frame.jpg`（单帧） |
| `web/console/index.html` | 中栏第一张「实时画面」卡：接管开 / 放开关 / 轮内关、本轮结束自动恢复、不可用时每 2 秒重试并原样显示后端话术、帧龄 >3 秒自动重连 |
| `docker/` | `Dockerfile.patrol` 装 ffmpeg；`patrol-entrypoint.sh` 的 `preview` 角色；compose 的 `mushroom_preview`（健康判据用容器内 `/healthz`——503 = 还没有帧）；`web/console/nginx.conf` 对 `/api/` 关掉 `proxy_buffering`（否则 MJPEG 会被攒成"延迟十几秒"） |

两处**实现时**才明确的决定：

1. `/api/preview` 会**先打开上游、看到状态码再返回**：`StreamingResponse` 一旦返回状态码就
   定死了，上游 503（正在连相机）会变成"200 + 空流"，页面只看到一张永远不出现的图。
2. §4 的"轮内拒绝"由**服务端**兜底：console 每转发 8 块（5 fps 下约 1.5 秒）回头检查一次，
   轮次一开始就把**已经开着**的流也断掉——不能指望页面自觉（标签页卡住、页面是老版本时，
   规则就没人执行了）。页面那一侧同时会主动关掉并把理由显示出来。

## 补记（2026-09-21）：改用相机原生 2880——服务器够、链路不够，代价是帧率

现场提出"只有一个摄像头，这里考虑视频流用原始分辨率"。做了完整取数，中间一度回退到
`1280×15`，**最终仍按现场选择保留原生 `2880×15`**：服务器侧完全够，瓶颈只在链路，
所以这是一笔"清晰度换帧率"的明账（取舍见文末「决定」）。数据留档，免得下一个人重复丈量。

### 相机源与三档成本（实测，不靠外推）

源流是 **2880×1616 hevc @12 fps**（`ffprobe` 声明 + 真解码 15 s = 180 帧、两次一致；
⚠️ 09-17 量到的是 15 fps——DVR 侧被人改过）。
⚠️ **2026-09-22 中午复测：源流又变回 15 fps**（七路信号见文末「补记二」）——帧率是**会变的
量**，任何取值决策前必须按 PTS 口径复测，别把本文任何一个帧率当常量。子码流 `Channels/102`
同为 2880×1616，
**没有更小的码流可选**，唯一的缩放就是我们自己的 `-vf`。

一次性容器、同滤镜只换 `scale`、`-r 12 -q:v 7`、36 帧数字节：

| scale | 每帧 | @12fps | 说明 |
| --- | --- | --- | --- |
| 1280 | 61.7 KB | 5.92 Mbps | 现状 |
| 1920 | 129.4 KB | 12.42 Mbps | |
| 2880 | 267.5 KB | 25.67 Mbps | 相机原生 |

字节数是**次线性**的（像素 ×5.06 → 字节 ×4.33）；按像素数线性外推会得到 ≈38 Mbps。

### 服务器侧完全够，卡在链路上

`PREVIEW_SCALE=2880` 上机后实测（容器 `cpus: 1.5`）：

| 观察点 | 结果 |
| --- | --- |
| 产出 | JPEG **2880×1616**、单帧 252~292 KB、`-r 15` 稳定 15.0 fps、`restarts: 0` |
| 开销 | CPU **0.33 核**（原 0.27）、内存 375 MiB（限 512）⇒ 编码不是瓶颈 |
| **生产机本机订阅** | 10 s 收到 39 845 888 B = **31.9 Mbps**、**152 帧 = 15.2 fps** |
| **经 VPN 订阅** | 15 s 收到 18 171 646 B = **9.69 Mbps**、只有 **70 帧 ≈ 4.7 fps**（10 s 那次 9.83 Mbps，一致）|

即 **服务器能送 31.9 Mbps、VPN 只收得下 ≈9.8 Mbps ⇒ 每 3 帧丢 2 帧**，画面"有影但一顿一顿"。

### 测量方法上的坑（本次最值钱的一条）

先前"现场 VPN 实测可用 ≈28 Mbps"是拿**一张 766 KB 图**测的——0.2~0.3 s 就传完，那是
**突发值**。同一条链路对**持续**流量（10~15 s）只有 **≈9.8 Mbps**；当天还量到过
**0.65 Mbps** 的低谷（连续两轮 12 s / 977 KB，同时 `viewers: 0`、宿主机网卡近零流量
⇒ 不是被预览占满，是链路本身在波动）。

⇒ **判断"能不能承载一路视频流"，必须测持续吞吐、并且用流本身测**
（`curl <URL>/api/preview` 数秒数字节），不能拿短文件下载的突发值外推——两者在这条 VPN 上
差 **3 倍以上**。这条纪律对"要不要往上调 `PREVIEW_SCALE`"同样适用。

### 决定：**保留原生 2880**（现场明确接受代价）

> ⚠️ **此决定仅维持一天**：2026-09-22 现场经 VPN 实际使用后反馈"太卡"，实时预览已回退
> `1280×15`（抓拍仍取原图落库）。完整记录见文末「补记（2026-09-22）」，下文原文留痕。

这不是"原生 vs 降采样"的选择，而是"**清晰度 vs 帧率**"的交换——服务器侧两种都做得到，
链路只肯给 ≈9.8 Mbps：

| 取舍 | 拿到 | 代价 |
| --- | --- | --- |
| 1280×15（原档） | 15 fps 满帧率 | 4K 满屏时框 1925px，被放大 1.5×、偏软 |
| **2880×15（现行）** | 4K 满屏下 1.5× 过采样、明显更锐 | 经 VPN 只有 ≈4.7 fps（每 3 帧丢 2） |

**场站选后者**：预览的用途是"接管时看清对着哪儿"（见上文背景），场景基本静止，
锐度比流畅度更有用；而且预览是**按需开**（`viewers` 常态为 0），不看的时候不占链路。

- 上机只重建 `mushroom_preview` 一个容器（`--no-deps`），不碰 `mushroom_patrol`/
  `mushroom_console` ⇒ **不走启动预检、机构零接触**（patrol/console 的 Uptime 不归零、
  `data/runs` 不存在可证）。属于"只改取值"那一档：**不重建镜像**。
  回滚＝把 `.env` 的 `PREVIEW_SCALE` 改回 `1280` 再重建这一个容器（现场留了 `.env.bak-*`）。
- 前端 `--pv-k` 同步改成**相机原生 2880/1616**：它从此与 `PREVIEW_SCALE` 解耦
  （三档的成像比例只在偶数取整上差 <0.1%），不会再因为调档位而需要跟着改。
- **要做到"又原生又流畅"，唯一的路是换传输编码**：MJPEG 无帧间压缩，2880×15 就是
  32 Mbps 打底；换 H.264/HLS 后同画质约 2~5 Mbps，能进这条链路。代价是本文决定 1 的
  "`<img>` 直接播、零 JS 播放器"不再成立（要 MSE + 播放器），属于另一次立项。

### 顺带一条独立发现

`PREVIEW_FPS=15` 而源流是 **12 fps** ⇒ **1/4 的输出帧是重复帧**，而重复帧一样要花整帧带宽
（MJPEG 无帧间预测），上游日志 `More than N frames duplicated` 即此。
"帧率对齐源"这条纪律要**定期复测**，别把一次量到的值当常量。
⚠️ **2026-09-22 中午复测作废本条**：源流已回 15 fps、`-r 15` 零重复帧，本条发现不再成立；
用户指令"对齐 12"因此失去对象，决定维持 `PREVIEW_FPS=15` 不发版（七路证据见文末「补记二」）。

## 补记（2026-09-22）：原生 2880 只维持了一天——现场经 VPN 体感卡，实时回退 1280

上一节"保留原生 2880"的取舍现场实际用下来**不成立**：锐度的收益是渐进的，卡顿的代价是
每 3 帧丢 2——预览的用途是"接管时边挪边看"，一动就糊比静态偏软更难接受。现场裁定：
**实时预览回退 `1280×15`；抓拍仍取原图落库，不受影响**（抓拍走独立采图服务：
`manual_exec._capture` → 采图服务 → MinIO 2880×1616 → `append_index` 落库，
与 `PREVIEW_SCALE` 完全无关，本节所有改动都碰不到它）。

已执行（2026-09-22，prod 10.77.77.39）：

| 项 | 动作 | 验收 |
| --- | --- | --- |
| 后端 | `.env` `PREVIEW_SCALE` 2880→1280，只重建 `mushroom_preview`（`--force-recreate --no-deps`） | `-vf scale=1280:-2`、JPEG 1280×718、≈62 KB/帧、`restarts: 0`；patrol/console Uptime 不归零、`data/runs` 不存在 ⇒ 机构零接触 |
| 前端 | `--pv-k` 2880/1616→**1280/718**（页面-only 发版，不重建镜像） | 线上字节 sha256 == git LF blob；探针四档视口 `barEachPx` 全 0 |

`--pv-k` 一并回退的理由：黑边为 0 的判据是**框与帧精确相等**。上一节把它改成"与档位
解耦、恒写相机原生比例"（差 0.03%），在 4K 满屏（框宽 1925px）上就是一条 1px 的边。
所以 `--pv-k` 的正确语义是"**当前 `PREVIEW_SCALE` 档位实际输出帧**的宽高比"
（`scale=W:-2` 从 2880×1616 偶数取整：1280→718 / 1920→1078 / 2880→1616）——
改档位必须同步改它，并用探针复核（`.scratch/visual/live_probe.py`，`barEachPx` 全 0
才算数，别用"我没看见黑边"结案）。

留给下一次的三句话：

- 这条链路的持续吞吐 ≈9.8 Mbps（burst 24~32 是假象，见上一节）⇒ **原生 2880 的实时
  预览在此环境下不可行**，除非换 H.264/HLS（同画质 2~5 Mbps，代价是零 JS 播放器不再成立）。
- `PREVIEW_FPS=12`（对齐源流 12 fps）仍是白捡的 25% 带宽，现场两次都未取。
  > ⚠️ **2026-09-22 中午复测作废**：源流回到 15 fps ⇒ `PREVIEW_FPS=15` 已对齐、零重复帧，
  > 没有免费带宽可省；此时改 12 是丢 3/15 真实帧的降帧（省 ≈20% 字节），不是对齐。
  > 用户定：维持 15。七路证据见文末「补记二」。
- 预览取值的改动是"只改取值"那一档：改宿主 `.env` + 只重建 `mushroom_preview`，
  脚本 `.scratch/visual/release-preview-scale.sh <宽度>` 幂等可重跑（带备份+复核）。

## 补记二（2026-09-22 中午）：复测源帧率 = 15——"对齐 12"失去对象，维持 `PREVIEW_FPS=15` 不发版

用户指令「对齐12并重新发版」的依据是上一节记的"源流 12 fps"。按 §10.1「对齐前必须复测」
的纪律先在 prod 上量了一遍，**结论与预设相反：源流当前是 15 fps**，七路独立信号全部一致
（prod 10.77.77.39，2026-09-22 11:53~12:10，一次性容器直连 DVR，不经过预览链路）：

| # | 信号 | 结果 |
| --- | --- | --- |
| 1 | 一次性容器真解码，ffmpeg 退出行 | `frame=216 / time=00:00:14.40` ⇒ **15.0**（PTS 口径） |
| 2 | `ffprobe` 声明（101 与 102 都量） | `r_frame_rate=15/1`、`avg_frame_rate=15/1` |
| 3 | ffmpeg filter config 行 | `frame_rate: 15/1`、每帧 duration 6000/90000 = 1/15 s |
| 4 | `showinfo` pts 序列 | 163 帧、0→10.8 s、间隔**全部** = 0.0666667 s，无一处跳变 |
| 5 | `mpdecimate` 内容去重 | 172 帧只掉 ~3 帧，且每帧 luma 校验和都不同 ⇒ 15 个**真实独立**帧 |
| 6 | 生产 `mushroom_preview` 日志 | `-r 15` 连跑 **67.4 min 零 `duplicated` 告警** |
| 7 | 反证阈值 | 源若为 12：3 次/秒 × 3333 s ⇒ **55.6 min 必触发** `More than 10000 frames duplicated`（09-21 实测出现过），本次静默 |

⇒ `PREVIEW_FPS=15` 对 15fps 源**已经对齐、零重复帧**，"白捡的 25% 带宽"不存在；
此时改 12 是**丢 3/15 真实帧的降帧**（7.5→5.9 Mbps），不是对齐。
**决定：维持 `PREVIEW_FPS=15`，不发版**（prod `.env` 未动、`mushroom_preview` 未重建、
patrol/console 未碰；用户在场选定）。

### 源帧率是个会变的量，不是常量

09-17 = 15 → 09-21 = 12 → 09-22 中午 = 15。DVR 侧编码配置被改过（至少一次）；
09-21 的"12"也无法排除是墙钟口径误差（RTSP 建连吞 2~3 s，"15 s 数 180 帧" ≈ 12.5 s
媒体 × 15fps = 187）——两种可能从现有证据无法区分，但**结论相同：用前必须复测**。
两条纪律由此落地（已补进 skill §10/§10.1）：

1. **对齐前必须复测，且必须用 PTS 口径**：`timeout N … -f null -` 看退出行的
   `frame=/time=` 相除（或 `-t N`、`showinfo` 的 `pts_time`）。墙钟口径会被 RTSP 建连
   系统性低估；`grep 'Parsed_showinfo'` 数帧还会把 2 行 config + 每帧 2 行
   （`n: pts:` + `color_range:`）都数进去，帧数翻倍（本次 163 帧被数成 328）。
2. **`duplicated` 告警是免费探针**：`-r` 一旦大于源，重复帧按帧累积，约 55.6 min 必在
   `mushroom_preview` 日志里喊 `More than 10000 frames duplicated`（`-loglevel warning`
   也进日志）——源帧率什么时候又变了，`docker logs mushroom_preview | grep -i duplicat`
   一眼便知。当前（15 对齐）这条探针应当是**永远沉默**的；哪天它响了，就是 DVR 又被改了。
