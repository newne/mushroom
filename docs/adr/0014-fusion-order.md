# ADR-0014：两个子系统"融合"的顺序（先基线、再依赖升级、最后才动结构）

日期：2026-09-14
状态：已接受

## 背景

ADR-0012 把两个工程合成了一个仓库，但保留了**两份锁、两个 uv 项目**，并把算法侧的
`src/`、`docker/` 当作不可动（那会儿的理由是"别打断现场发版"）。此后确认：算法工程
也是同一个作者写的，**可以动**——于是"融合"从"同一个仓库"变成"同一套结构"。

但"可以动"不等于"可以随便动"。三件事各自的真实代价（都是实测/数出来的，不是估计）：

| 事项 | 实际规模 | 现在做的后果 |
| --- | --- | --- |
| 把 `src/` 下 **18 个顶层目录**收成一个包的子包 | 跨包 import **383 行**要改，外加 `docker/build.sh` 的 `obfuscate src`、Dockerfile 的 `COPY dist/src/`、以及现场正在跑的部署 | 一次改不完就会留下"一半新结构一半旧结构"，而现场发版依赖这些路径 |
| 合并两份 `uv.lock` 为一份 | 根项目那份锁**与它自己的 `pyproject.toml` 就不自洽**（在算法工程自己的提交 `a615909` 上用 `uv lock --check` 即失败，已用纯净 worktree 复现）⇒ 任何触碰它解析的动作都会**全量重解** | 实测一次 `uv lock` 动了 **84 个包**（`fastapi 0.133→0.136`、`transformers 5.2→5.9`、`redis 7.2→8.0`、`rich 14→15`），那不是"整理结构"，那是**一次无人评审的生产依赖升级** |
| 动 `src/configs/settings.toml`（加一条巡检地址） | 工作区里有 **62 项未提交的在建重构**（10 删 52 改，`src/scripts` 28 项、docs 11 项、`tests/functional` 5 项），其中就包括 `settings.toml` | 我的改动会与在建重构混进同一个 diff，事后分不清哪行是谁的、哪次改动引入了问题 |

## 决定

融合按**这个顺序**做，每一步都能单独验收、单独回退：

1. **先把算法工程的在建重构落成基线快照**（提交 `cba6a40`，标题明确标注"非本次合并所写"）。
   在此之前，任何新改动都无法归因——这不是洁癖，是排障的前提。
2. **再做一次独立的依赖升级**（把根 `pyproject.toml` 与 `uv.lock` 弄回自洽）。
   它必须是一次**单独的、要评审的**变更：84 个包的版本变化需要自己的验收
   （至少覆盖启动、调度器注册、视觉 job、DB 连接），不能夹在结构整理里。
   在这之前**两份锁保持不变**。
3. **最后才动 `src/` 的包结构**。它需要一次机械但全量的 import 重写（383 行）+ 构建脚本
   同步修改 + 一次现场发版验证；放最后是因为它最不可逆，也最容易与上面两件事互相掩盖。

`settings.toml` 现在**可以**改了（第 1 步之后它就是干净的），但巡检触发地址仍然优先走
环境变量：它是**另一个子系统**的地址，放进算法侧的 configs 会让两边改配置互相牵动。

## 后果

- 顺序反了会**静默**产生两种损失：把 84 个依赖升级混进"整理结构"（无人评审的生产变更），
  或者把在建重构混进别人的 diff（事后无法归因）。两者都不报错。
- 巡检侧的步骤 4（手动控制）与步骤 5（上机）**不依赖这三件事**，可以并行推进；
  只有"融合成一套结构"要排在它们之后。
- 两份锁继续存在，代价是维护两处，收益是"合并没有改变生产依赖"这件事**可验证**。
