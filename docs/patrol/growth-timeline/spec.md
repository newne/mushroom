# 长势时序（growth-timeline）：当前批次「每节点 × 时间」的轨迹视图

Status: ready-for-agent
归属：后端（端点）+ 前端（历史 tab）
依据：用户 2026-10-16 裁定 —— ①「节点」按**站位**做主轴、**框**做聚合；② **P0 先上覆盖/质量时序**，不干等测量接通；③ 时间轴用**真实时间 + 生长天数双刻度**
关联：docs/patrol/env-baseline/spec.md（环境同期对照）；env-analysis 票 23（同期基线）、24（按生长天数的分布）；growth-algo 票 21（簇级量测与首条曲线）

## Problem Statement

历史 tab 里现在只有一张「生长曲线」卡，它有两个硬伤：

1. **只画聚焦站位对应的那一个框**（`#curve`，跟着 `hist.focusedStationId` 走）⇒ 看不到"这一批里 48 个节点**各自**在怎么走"。
2. **x 轴用的是数组下标**（`i * step`），不是时间 ⇒ 巡检节奏一抖，时间轴就在骗人。而"从时间维度看"恰恰是本规格的全部意义。

现场真正要回答的是：**当前批次（611：2026-09-30 入库）从时间维度看，每个节点发生了什么、哪片区域断了、这批整体在怎么长。**

## 数据真相（它决定分期，必须先摆出来）

| 数据 | 现状（2026-10-16 实测） | 支撑什么 |
| --- | --- | --- |
| `rounds` | 84 轮（2026-09-13 起） | 巡检节奏 |
| `images` | 4,022 帧 | 覆盖 / 失败 / 重复 |
| `environment` | 2,728 小时行 | 温湿 CO₂ + **光照循环制度** |
| **`measurements`** | **0 行** | ❌ **"蘑菇变化"本身现在没有数据源** |
| `/growth/room` | 60 个框，**全部 `no_prev`** | ❌ 同上 |

⇒ **P0 画"能画的"**（每节点每轮的覆盖与质量），把长势曲线的**插座先留好**；测量一接通，同一条时间轴立刻有内容。

## Solution

在历史 tab 增加一条「时序」主线，三块视图 + 一个供给端点：

- **A 小倍数矩阵**：48 个站位按 **12 列 × 4 层**排（**与平面图物理布局一致**），每格一张 sparkline。
- **B 单节点放大**：点某站进入，大图用**双刻度时间轴**，可叠加环境带。
- **C 库房分位数带**：中位 + IQR，回答"这批整体在怎么长"。
- **供给**：`GET /timeline` **一次拿回「每节点 × 每轮」矩阵**，不在页面上发 N 次请求。

## User Stories

1. 作为现场人员，我要在历史 tab 一眼看到**本批 48 个节点**的时间轨迹，而不是一个一个站位点过去。
2. 作为现场人员，我要能一眼看出**哪片区域、哪一层断了**（哪个站位哪些轮没有帧）。
3. 作为现场人员，我要时间轴是**真的时间**，巡检间隔不规律时不要骗我。
4. 作为现场人员，我要同时看到**生长第几天**，因为这批的窗口是第 2–25 天。
5. 作为现场人员，我要点开单个节点看细节，并把**环境（含光照循环制度）**叠在同一条时间轴上。
6. 作为现场人员，我要看到**这批整体**的中位与四分位带，而不是被单个坏点带跑。
7. 作为现场人员，**没测到就是没测到**——不许画成一条零增长线，也不许插值补点。
8. 作为开发，我要端点一次返回矩阵，避免 48 次请求把页面拖垮。

## Implementation Decisions

### 端点契约（seam）

```
GET /timeline?zone=611&batch_id=611|2026-09-30&metric=coverage
```

- `metric`：P0 只认 `coverage`；P1 增 `growth`。
- 返回：
  - `batch`：`entry_date` / `batch_no` / `day_now` / `day_max`（=25）
  - `axis`：`t0` / `t1` / 生长天数刻度点
  - `nodes[]`：`node_id`（站位）/ `layer` / `col` / `box_id` / `points[]`
  - `points[]`：`ts` / `day` / `round_id` / `has_frame` / `n_frames` / `ok_rate` / `dup` / `growth`（P1，缺即 `null`）
  - `room_band[]`：`ts` / `day` / `p25` / `p50` / `p75` / `n`
  - `notes[]`：数据侧说明（沿用既有 `notes` 手法）
- **节点主轴 = 站位**，`box_id` 只作聚合与既有「生长曲线」卡的对接键。

### 三条硬规则

1. **x 轴永远是真实时间戳**（`ts`），生长天数由 `batch.entry_date` 派生为**第二刻度**；**禁止再用数组下标当 x**。
2. **`null ≠ 0`**：没有测量行 ⇒ `growth: null`；没有帧 ⇒ `has_frame: false`。缺口**断开画**，不插值、不补零、不连线跳过。
3. **零前端依赖**：手写内联 SVG（沿用页面既有手法），不引入任何图表库。

### 数据量与性能

48 站 × 16 天 × 8 轮 ≈ 6,000 格 ⇒ 单次 JSON 约 200–400 KB，可接受；页面一次渲染，不轮询。
> 若将来帧数暴涨，再谈"按窗口分页"，**本期不做**。

## Testing Decisions

- 端点：矩阵形状（每站每轮一格）、双刻度派生（`day` 由 `entry_date` 算出）、`null` 语义（无测量行时 `growth` 必须是 `null` 而不是 0）、缺批次的处理。
- 前端：无头回归（既有 `docs/patrol/console-ui/verify-page.js` 那套）——小倍数格数 = 站位格数；**把"断线"改成连线会红**；把 `null` 画成 0 会红。
- 真数据核对：用生产 `images`/`rounds` 的 84 轮 × 48 站做一次对账（每轮每站格数应等于该轮实际帧归属）。

## Out of Scope

- 不做 mm 实际尺寸（本批仍是像素与包相对量）。
- 不做预测 / 外推 / 拟合。
- 不引入图表库或任何前端依赖。
- 不改既有「生长曲线」卡的定位（它仍是单框详情的入口）。

## Further Notes

- **P1 的前置是测量管线**（现役 `--measure` 默认关闭、现场阈值未定标）；本规格把插座留好，不为它造数据。
- 与 **env-analysis 票 24**（按**生长天数**的分布 / 箱线图）互补：那是分布，这是轨迹。
- 与 **env-analysis 票 23**（同期基线）互补：那是跨批对照，这是本批轨迹。
