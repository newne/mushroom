# ADR-0006：巡检台与后端采用 REST + 异步任务 + 轮询，历史读取合并双源

日期：2026-09-10
状态：已接受
背景：巡检台（console，ADR-0003）要同时驱动"秒级阻塞的运动命令"与"跨机读取的历史数据"。
`Fmc4030.goto` 一次调用含两个速度段、到位等待与 0.4s 振动衰减，同步 HTTP 会让浏览器连接
长时间挂着；而历史图像索引有两处来源：patrol 本地（已采未同步）与 prod（已同步，ADR-0001）。

## 决定

- **控制面是 REST**：参数校验**同步**完成（非法立即 `400`），执行**异步**——合法命令返回
  `202 + job_id`，前端以 **1s 轮询** `GET /api/status` 获取位姿、当前 job 与进度。
- **不用 WebSocket / SSE**：实时性需求是"人看着机器动"，1s 粒度的轮询足够；现场常见的旁路
  代理与防火墙对长连接的破坏成本高于省下的那点带宽。
- **历史读取合并两个来源**：console 查询时把"patrol 本地 outbox 中未同步的索引"与"prod
  已同步的索引"并起来返回，避免刚拍完的图查不到。
- **图像一律经 console 转发**（`GET /api/image`）并由 console 生成、按 `object_name` 缓存
  缩略图；浏览器不直连 MinIO，也不持有 MinIO 凭据（ADR-0003）。

## 决定理由

- 运动端点必须"同步校验、异步执行"：越界坐标/未持有会话这类错误应立即反馈，而机械到位
  时间不可预测，把它塞进 HTTP 响应周期里会让超时策略变成猜谜。
- 合并双源只多十几行查询代码，换来"拍完立刻可见"；若只读 prod，现场刚采的图要等一个
  outbox 同步周期才出现，操作者会以为拍照失败。

## 后果

- 前端所有状态刷新走同一个 `GET /api/status`，实现简单、易排查（打开浏览器就能看到在发什么）。
- 轮询间隔是**唯一的实时性旋钮**：若将来出现"多人同时看"或"更高刷新率"需求，再评估 SSE。
- 缩略图缓存是 console 的本地状态，需定义失效策略（按 `object_name` 缓存即可，图像本身不可变）。
- `GET /api/status` 顺带返回**最近 N 条指令历史**，界面底部的日志栏不需要单独的接口。
