# 07 — `src/` 里硬编码的 Redis 口令：**仓库有，四个现役镜像都没有**

**归属：** 发版官（只读核查）
**日期：** 2026-10-14
**结论一句话：** `src/global_const/cache_client.py` 的兜底分支把 Redis 口令**硬编码成字符串字面量**（在仓库里、也在 **git 历史**里）；
但**四个现役镜像里都没有这一行** —— 所以它**目前没有**随任何镜像推到 registry。**真正的暴露面是仓库，不是镜像。**

## 1. 仓库侧

- 文件：`src/global_const/cache_client.py`
- 行为：`settings.redis.*` 取不到时（`AttributeError` 分支）**把口令写成字符串字面量**，随后用它建 `redis.ConnectionPool` / `redis.Redis`；
  再失败才 `conn = None`。
- 本票**不抄录口令值**（按"凭据不进聊天/仓库/票据"的规矩），定位到文件 + 行为即可。
- ⚠️ 该文件**由 git 跟踪** ⇒ 口令**已进仓库历史**，任何有仓库读权限的人都能取到。**这是主要风险面。**

## 2. 镜像侧（2026-10-14 11:5x 只读实测）

方法：`docker run --rm` 进各现役镜像，只查 `cache_client.py` 是否存在、以及是否含
「`redis_password` 被赋成**字符串字面量**」这一**结构模式**（按模式匹配，**不打印任何值**）。

| 镜像 | `cache_client.py` | `redis_password` 赋值 |
| --- | --- | --- |
| 算法侧 `mushroom_solution:0.1.0-20261006222420-121f1b9` | **在**：`/app/global_const/cache_client.py` | **0 处**（含 `redis_password` 的行数 = **0**） |
| 巡检 `mushroom_patrol:0.1.0-20261013204311-89e4a54` | 不在 | — |
| 巡检 `mushroom_patrol:0.1.0-20261014112224-46ca2f2`（今天新上线） | 不在 | — |
| 采图 `mushroom_capture:0.1.0-20261013200745-f584691` | 不在 | — |

⇒ **结论：四个现役镜像都不含这个字面量。** 算法侧镜像里那份 `cache_client.py` 与仓库当前版本**不同**
（它没有这段兜底赋值）——也就是说，那段兜底是**先天的仓库侧问题**，还没被任何一次构建带进镜像。

## 3. registry 侧

同一 tag 的本地镜像就是 push 上去的那份（`docker push` 按层 digest 上传，本轮实测现役 tag 的 registry digest 与本地一致）。
**历史 tag 没有逐一拉远端核对** ⇒ 口径为：**"现有四个现役 tag 不含它"已确认；"registry 上是否存在含该字面量的历史镜像层"——未确认。**

## 4. 建议（本票不执行，等裁定）

1. **改成 fail-fast**：`AttributeError` 分支直接报错，不要内嵌口令 —— 与 `PGSQL_DSN_FILE` 那条
   "没有 DSN 就报错、绝不回退"同一口径（票 `env-analysis/issues/13`）。
2. **轮换那把 Redis 口令**：它已经进 git 历史，删代码不等于解除暴露。
3. 要彻底可另开票评估 git 历史清理（成本高、需全员协调）。

## 5. 与 A′ 判决（票 06）的关系

这条是票 06 判 A′ **"不可接受"**的独立理由之一：**`src/**` 进 patrol 镜像 = 这段口令随镜像推上 registry**。
现在有了实测数字：**当前确实还没有**，但只要走 A′ 就会立刻有；而巡检镜像一旦带上 `src/**`，这个 tag 就会成为第 5 个含口令的镜像。
