# ADR-0018：Z 轴原点在**顶端**（靠近电机端），坐标向下为正 —— 修正 Z 的回零方向与框架

日期：2026-09-15
状态：已接受（用户现场指出："z 轴回零方向反了，最上面是原点；y 轴最左面是原点，
都是靠近电机的为原点"）
修订：ADR-0007 的 Z 行与 §四结论、ADR-0010 §四的 Z 记录、ADR-0008 的 Z 软限位。

## 背景

现场指出 Z 的回零方向反了。核对后确认这是**真错**，且错在两个层面：

1. **回零找错了开关**。说明书 §三.2 定死了两个开关的物理位置（这句话在本仓库里抄过两次，
   见 `docs/patrol/fmc4030-camera-scan/spec.md` §"轴 0 (X) … 正限位（远离电机端）"
   与 `motor-command-review.md` §2.3）：

   > **正限位位于远离电机端，负限位为靠近电机端。**

   本机 Y 的电机在**左端**、Z 的电机在**顶端**，而两轴的原点都在靠近电机的那一端
   （用户 2026-09-15 确认）。于是：

   | 轴 | 电机位置 | 原点 | 应当回零的方向 | 代码里原来写的 |
   | --- | --- | --- | --- | --- |
   | Y | 左端 | 左端 | 负限位（`homeDir=2`） | ✅ `2` |
   | Z | **顶端** | **顶端** | 负限位（`homeDir=2`） | ❌ `1`（= 远离电机端 = **底部**） |

   即：Z 一直在往**下**跑到远端开关，把**底部**当成了坐标 0。

2. **坐标框架跟着反了**。控制器回零时把**开关所在处**置为 0，而坐标只能朝**远离开关**
   的一侧增长。Z 改成"往顶端回零"之后，0 落在顶端、底部是 **+212**——所以行程是
   `0…212`（向下为正），而不是原来的 `-212…0`（向上为正）。

第 2 条是这次修订里最容易漏的一步：只改 `home_dir` 而不改坐标范围，会让每一个绝对目标
都跑到反方向去（旧的 `z=-21.2` 会被解释成"顶端往上 21.2 mm"，直接压限位）。

## 决定

1. **两轴同构**：原点都在**靠近电机**的那一端，回零都找**负限位**（`homeDir=2`）。
   `_Y.home_dir = _Z.home_dir = HOME_DIR_NEGATIVE`。
2. **Z 的行程改为 `0 … 212`，正方向 = 向下**（离开顶端电机）。不变式
   "`home_position` = 原点 = 0" 对两轴仍然成立，且有测试守护。
3. **`AxisProfile.positive_towards`** 新增字段（`"right"` / `"down"`）：把"坐标增大往哪走"
   变成机器参数的一部分，供 `patrol.framing` 派生 `sign_z`（图像方向 → 轴方向）与页面文案。
   以前这句话只活在注释里，改一处漏一处。
4. **站位数据迁移**：`z_new = -z_old`、`trim_z_new = -trim_z_old`（物理位置不变）。
   工具：`patrol-migrate z-frame --stations <path> [--dry-run]`，落盘前自动备份、
   表里出现 `z > 0` 就拒绝重复执行。
5. **控制器侧要重整定 Z 的软限位为 `0…212`**（ADR-0008）：`--dry-run` 与巡检启动前的
   `check_soft_limits()` 会把"控制器还是旧框架"这件事拦下来（fail-closed），这是这次
   迁移的安全网。
6. **页面**：平面图第 1 层画在最上（从原点侧起算）、标题与坐标范围文案改成"Z 向下"、
   点动按钮标出物理方向（`Z +（下）` / `Z −（上）`）。
7. **文档更正**：ADR-0007 §四那次"Z 以 `homeDir=1` 从 −40 回到 0.000"的实测**并没有证明
   0 在顶端**——它证明的是"控制器在自己找的那个开关处置零"。当时把控制器的 0 当成了顶端，
   于是这条错误结论被写进 `motion_profile`、spec 与 gap-list，一路传到今天。教训：
   **"实测吻合"要写清吻合的是哪条物理事实**，否则它只是把假设洗了一遍。

## 为什么不能只改一个方向（或者只改数据）

三条路都试算过，只有第 3 条自洽：

| 方案 | 结果 |
| --- | --- |
| 只改 `home_dir`，坐标仍是 `-212…0` | ❌ 顶端变成 0、底部 `+212`，而代码以为 `-212` 在下面 → 每个目标都跑反 |
| 只改数据 `z += 212` | ❌ 那是"加"而不是"取反"：第 1 层会被送到第 5 层的位置（物理位置变了） |
| 改 `home_dir` **且**镜像框架（本次采用） | ✅ 原点在顶端、坐标单侧向下增长，与控制器读回一致 |

> 另一条理论上可行的路是**把 Z 电机的相序反过来**（正方向就会朝上，框架不变），
> 但那要动硬件接线，而且"哪一端是正限位"会跟着变；在没有方向反转参数的控制器上，
> 软件侧做不到。记在这里是为了将来有人问"为什么不干脆让它向上为正"。

## 后果

- **上机必须重做一次回零**（`homeDir` 变了）+ 重写 Z 的软限位；在此之前**不许下发任何
  绝对坐标**。清单见 `docs/patrol/prod-deploy/z-frame-cutover.md`。
- 站位表迁移是**幂等保护**的（第二次执行会报错），迁移前后 `patrol-migrate --dry-run`
  都能一眼看到换算结果。
- 历史图像**不受影响**：图片按 `station_id` 关联，物理站位没变。但要注意：在旧框架下
  实拍过的那些图（例如 2026-09-13 的 m0 单站图）"当时机器实际去的是镜像后的位置"——
  prod 里几乎没有这类数据（一轮巡检都还没跑过）。
- `framing` 的 `sign_z` 默认值从 −1 变成 **+1**，且改为从 `positive_towards` 派生；
  现场若换相机朝向，仍然用 `--framing-sign-z` 显式覆盖。
